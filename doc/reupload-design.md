# 转发消息下载后重新上传

## 范围与命令

保留 `just upload` 的本地文件上传功能，新增 `just reupload`。两个命令共用项目进程锁、Bot 凭据和 Telethon 会话，不能同时运行。无需用户账号登录、Bot API 本地服务器或新增第三方库。

`reupload` 监听配置指定的一个频道或与 Bot 的私聊：接收人工转发的消息，先完整下载到硬盘，再使用本地文件重新上传到同一个会话。频道中 Bot 必须有接收频道更新和发布消息所需的权限。推荐使用单独的私有备份频道。不读取原频道历史、链接或评论区；收到什么，就备份什么。禁止转发的内容无法通过这个入口导入。

支持普通文字、图片、视频、文件，以及图片/视频相册。保留收到的文字、caption、文字实体、媒体类型和顺序；同一相册作为一个上传单位，内部按接收消息 ID 排序。批量转发按目标会话中的消息 ID 顺序串行处理，当前任务完成后才上传下一项。不会删除用户转发进来的原消息。新上传消息没有转发标记，不会再次入队。

只备份消息主体，忽略消息附带的所有按钮和键盘，包括网址按钮、回调按钮、回复键盘和强制回复提示；不执行按钮操作，也不将按钮重新发送。此前因按钮而中断的任务，直接重新运行 `just reupload` 即可继续，无需清理队列或重新转发。

这是内容备份：新消息的发送者、消息 ID、时间、浏览数和原评论关系由 Telegram 决定。图片重新作为图片上传时可能被 Telegram 处理，无法承诺文件字节不变。暂不支持的消息类型应明确停止处理并保留队列，不静默丢失内容；不自动压缩、切片或把图片改成文件。

## 配置

保留现有顶层 `bot`、`profiles`，新增可选的 `reupload`：

```json
{
  "reupload": {
    "chat_id": null,
    "download_dir": null,
    "keep_downloads": false,
    "retries": 5
  }
}
```

`chat_id` 填接收及返回备份消息的同一个会话 ID，例如 `-100...`；私聊时填写已主动联系过 Bot 的用户 ID。`chat_id: null` 只用于尚未配置的模板，启动 `reupload` 时必须补齐。

`download_dir` 省略或设为 `null` 时，使用系统下载目录下的 `tg-comment-uploader/reupload/`。Linux 读取 XDG 的 `user-dirs.dirs` 中的 `XDG_DOWNLOAD_DIR`，支持本地化目录和 `XDG_CONFIG_HOME`；未配置时使用 `~/Downloads`。也可填入自定义路径。相对路径相对项目根目录，支持 `~`。路径优先级为 `--download-dir` 参数、配置文件、系统默认目录。

默认在确认发送成功并保存返回消息 ID 后，自动删除该任务的本地下载文件。使用 `--keep-downloads` 可保留本次上传完成的文件；配置中的 `keep_downloads: true` 也可长期启用保留。未完成任务的文件用于恢复，上传过程中不删除。自动清理意图随确认记录一起保存，若中断在确认与删除之间，下次启动会重试清理；此前明确保留的文件不会因下一次普通启动而被删除。

旧配置仍可执行 `upload`。`reupload` 不依赖上传 profile，不从 profile 自动猜测备份目标。真实配置通过脚本添加缺失字段，不输出凭据或整个配置。

## 使用

1. 新建私有备份频道 B，把现有 Bot 加为管理员并允许发布消息；也可以使用已经向 Bot 发过消息的私聊。
2. 在 `config/config.json` 的 `reupload.chat_id` 填入 B 的数字 ID。不要填写源频道 A，也不要填写 Bot 的 ID。
3. 启动监听后，再把 A 中的消息批量转发到 B：

```bash
just reupload
```

临时指定下载目录（本次命令生效，直接使用给定目录）：

```bash
just reupload --download-dir ~/Downloads/my-backups
```

普通消息逐条下载、上传，相册先下载整组后一起发送。运行中用 Ctrl+C 或 SIGTERM 停止；再次运行同一命令恢复队列。不需要 `serve` 命令。

监听就绪后，连接持续至少 60 秒即视为稳定恢复。之后再断线，重连失败计数会清零，退避重新从 1 秒开始；短暂连接后立即断开仍累计失败。`reupload.retries` 限制连续失败的额外重试次数，默认 5，即首次尝试加 5 次重试；持续无法连接时仍会退出并保留队列。登录失败或清理退出时的等待不计入稳定时长。

默认自动恢复之前未完成的任务。只想处理本次启动后的新转发时，使用：

```bash
just reupload --no-resume
```

该选项仅对本次命令生效：启动前已有的未完成任务及其本地文件、随机 ID 都保留，本次不处理；启动前的离线转发更新也会忽略。新旧按消息转发到 B 的时间判断，精度为秒，不按原帖发布时间判断。本次新任务遇到断线仍会重试并继续，不会在重连时被归入旧任务。

下次执行 `just reupload` 或 `just reupload --resume`，会继续已有队列中的未完成任务。恢复的旧任务会追加在本次新备份之后，无法插回已经发送的消息之前。`--status` 始终统计全部已保存任务，包括本次跳过的旧任务。

所有操作都使用 `just reupload` 的参数。先停止旧监听，再按需启动：

```bash
# 放弃旧的未完成任务，再监听新的转发：
just reupload --discard-pending
# 清理已完成和已放弃任务的本地文件，再继续监听：
just reupload --delete-downloads
# 放弃未完成任务并清理所有已记录任务的本地文件，再监听：
just reupload --discard-pending --delete-downloads
# 上传完成后保留本地文件：
just reupload --keep-downloads
```

`--discard-pending` 和 `--delete-downloads` 在登录前执行，然后继续监听，共用 `upload`、`reupload` 的进程锁。这两个参数不能与只读的 `--status` 同用。`--discard-pending` 将未完成任务标记为已放弃，保留输入 ID、快照、发送随机 ID 和已完成记录，后续默认启动也不会恢复这些任务。还会保存截止时间，忽略本次操作执行时及之前的离线转发更新（按 B 中转发时间判断，精度为秒，包含当前秒），避免旧消息补收后重新入队。之后想重新备份已放弃的内容，需要重新转发。

单独放弃任务保留本地文件；`--delete-downloads` 清理当前会话中已完成及已放弃任务的下载文件，包含此前使用 `--keep-downloads` 保留的文件。未完成任务的文件继续保留用于恢复；需要一并删除时组合使用 `--discard-pending --delete-downloads`。清理不删除配置、Bot 会话或队列，已完成的任务记录仍然有效。清理失败时停止启动监听，放弃状态仍保留，重试 `--delete-downloads` 即可清理残余文件。放弃任务不会删除 Telegram 中的消息；若任务中断在最终发送阶段，频道里可能已经有备份，命令会提示发送结果不确定的任务数，再次转发前应先核对。

下载、校验本地文件和上传共用 `upload` 的终端进度组件，显示输入消息 ID、相册内序号、百分比、已传/总大小、平均速度、耗时和预计剩余时间。交互终端原地刷新，重定向输出时约每 10 秒记录一次。即使尚未收到第一个数据块，也会显示 0% 并刷新耗时；超过 15 秒没有新增数据会显示 `no new data`，该提示本身不改变重试策略。最终发送阶段使用同一个 Telegram 确认等待指示器，文件传输到 100% 后仍以 `confirmed` 日志为成功依据。接收新消息的日志会与活动进度条分行显示。

单文件下载支持断点续传，使用现有 Telethon 的 `iter_download(offset=...)`，无需新增登录或依赖。已接收的字节保留在 `media.bin.part` / `media.jpg.part`，对应的 `.part.json` 保存媒体身份、总大小、已保存长度和 SHA-256。每新增约 8 MiB 保存一次检查点；网络异常、取消或正常退出也会保存当前片段。重启先校验本地片段，再从相应偏移继续，最多为请求对齐重读断点附近不足 512 KiB 的字节，并比较重叠内容，避免重复拼接。已下载部分计入完成百分比；速度及 ETA 只根据本次新增下载量计算。

旧版本留下的 `.part` 文件会按所在任务的初始快照接纳，首次计算本地摘要建立检查点；这不能追溯检测升级前对该文件的修改。已有检查点时，内容、长度或媒体身份不符会明确停止，不将损坏片段拼入备份。强制终止或掉电后，超过最后有效检查点的尾部会丢弃并重新下载。全部字节下载并校验后才开始上传；下载完成的检查点随文件一起迁移、清理。若中断在文件完成与队列记录之间，下次也会校验并复用完整文件。

当前可处理队列全部上传确认后，会输出一次阶段完成汇总，然后继续监听：

```text
batch complete: 5 task(s), 5 message(s) confirmed; 0 active pending; waiting for new forwards (Ctrl+C to stop)
```

计数范围是本轮监听中自上次空闲以来确认的任务；相册算一个任务，消息数按成员数统计。提示只覆盖程序当前已收到的任务，不代表未来不会收到新转发。持续空闲不会反复刷屏，下一批处理完会再提示一次。等待相册成员、下载中、等待 Telegram 确认或任务失败时，都不会提前报告完成。`--no-resume` 暂缓的旧任务会另外显示 `deferred task(s) retained`，确认上传后仍未清理成功的本地文件会显示 `task(s) awaiting local cleanup`，不会混同为已处理完。

收到转发时即保存初始消息快照，包含文字、实体、媒体信息及下载引用。下载优先使用该快照，不在每个文件开始前强制重新读取原帖。引用仍有效时，删除 B 中的转发原帖不会让程序仅因原帖不存在而停止。

快照里的媒体引用不等于完整文件。Telegram 可能使引用失效，届时需要重新获取引用，见 [官方文件引用说明](https://core.telegram.org/api/file-references)。程序只在引用被拒绝后读取 B 中对应的消息，确认媒体类型、ID 和文件大小仍匹配，再单独保存新下载引用；最初的文字、格式、顺序和媒体元数据不变。刷新后的引用可跨重启复用。若原帖已删除且引用不可用，未下载完的文件仍可能无法恢复，已完成的本地文件会保留。

视频缩略图也会下载到同一消息目录的 `thumbnail.jpg`，保存独立的大小和 SHA-256，并随视频恢复、迁移及清理。优先采用原消息的静态缩略图，符合 JPEG、长边不超过 320 像素及 20 kB 保守上传限制时直接保留原始字节；超出限制时只处理缩略图。通过共享上传实现把图片另行上传为新的 `InputFile`，填写 [MTProto 的 `thumb` 字段](https://core.telegram.org/constructor/inputMediaUploadedDocument)，单条视频和相册均适用。视频文件、文字及视频属性保持原样。

原消息没有静态缩略图，或者旧缩略图引用已无法恢复时，会明确提示并用现有 FFmpeg 从已下载的视频抽帧生成 JPEG，不重新编码视频文件。网络暂时中断仍按原重试策略处理，不直接改用抽帧。原缩略图可用且符合限制时无需 FFmpeg。缩略图下载、校验或生成未完成时不发送视频；完成后才显示 `local snapshot ready`。本地缩略图被修改会停止发送，重启不会静默替换已经记录的缩略图内容。

一条消息或一个相册的全部文件（包括缩略图）下载并校验完成后，会显示：

```text
local snapshot ready for inputs 5,6,7,8: all content saved and verified; these input messages are no longer needed for this task
```

这时可以删除提示列出的 B 中原帖，后续上传使用本地文件。提示仅覆盖列出的输入 ID，不代表整个队列都已完成下载。看到 `queued` 或 `downloading` 就删除原帖，仍不能保证后续下载成功。

停止监听后，可离线查看已完成/待处理数量和状态文件位置：

```bash
just reupload --status
just --set config config/other.json reupload
```

下载保存在 `download_dir/<会话标识>/<任务>/<输入消息ID>/`，包含 `message.json`、媒体文件及适用时的 `thumbnail.jpg`。JSON 保存可读文字及文字实体；媒体按图片或文件类型下载，原文件名另存于元数据并在上传时恢复。队列位于 `.local/tg-comment-uploader/mtproto/reupload/<会话标识>/queue-v1.json`，保存完整的 Telegram 消息快照和校验值。不要删除队列来“重试”，否则已确认记录及随机 ID 会丢失。

修改下载目录后，下次启动会先迁移当前会话的本地文件，再开始监听；已完成记录、待处理任务、顺序及随机 ID 保留。相同文件系统直接移动，跨文件系统先完整复制并落盘，再更新队列路径、清理旧副本。迁移中断后用相同目录重试即可继续。若目标会话目录已有不属于本次迁移的文件，会停止并报告冲突，不覆盖它们。其他会话的文件不移动。`--status` 只显示目录和待迁移提示，不执行迁移。`--download-dir` 不修改配置，后续省略参数会按配置或系统默认目录再次迁移；长期使用自定义目录请写入配置。

## 模块与复用

- 配置定义和加载独立成模块，两个命令使用同一套校验。
- 现有 MTProto 上传拆分为会话管理、文件分片上传、消息发送及响应校验；同步 `upload` 和异步监听流程共用这些能力，包括文件完整性校验、最终请求超时和随机 ID。
- `reupload` 单独负责消息采集、相册归并、下载、持久队列和串行调度，不复刻底层上传实现。
- 新增或拆分的 Python 模块不超过 400 行；现有上传 pending 文件格式保持兼容。

## 持久化、顺序和恢复

使用单独的原子写入 JSON 队列。每条收到的转发消息立即持久化，再开始处理；监听与下载/上传共用一个 asyncio 循环，下载期间仍可接收入队。相册等待短暂静默期后归并，按消息 ID 排序；已经开始上传的相册若收到迟到成员，报告错误，避免静默拆错相册。

静默期为 2 秒；只有一个成员的相册会继续等待，不允许后续任务越过。顺序以消息在 B 中的 ID 为准，不按原频道 A 的发布时间重新排序。无法同时保持相册和全局顺序的交叉排列会停止处理。

队列绑定 Bot、配置路径和目标会话。任务保存输入消息 ID、相册 ID、原始文字及实体、媒体属性、下载路径及校验、稳定的发送 random_id、阶段和成功返回的消息 ID。先保存发送意图，再发最终请求；重启时已确认任务跳过，未确认请求使用相同 random_id 重试。未完成下载从有效检查点续传，已校验完成的文件直接复用。上传中断仍从当前文件的开头重新上传，最终发送继续使用原 random_id。

任务失败后停止推进后续任务，避免越过失败项破坏顺序；保留待处理任务，修复原因后重新执行命令。Telegram 限流等待和暂时网络错误按重试策略处理。正常中断保存状态并断开连接。监听需要保持运行：Bot 无权遍历频道历史，因此不能保证找回长期离线期间所有未收到的更新；已持久化的队列可以恢复。

防重按 B 中这一次转发的输入消息 ID 判断，不按来源或内容判断。用户重新转发同一条内容，会在 B 中产生新的消息 ID，应作为新任务重新下载并上传；同一个相册再次转发，也按新的一组消息完整处理。新任务不会复用另一任务的下载文件。无需额外参数。

同一输入的更新被重复投递、断线补收或重启后再收到时，只保留一个任务。中断恢复继续使用原任务、已校验的本地文件和持久化的发送 random_id，已确认任务不再发送。即使新旧任务内容完全相同，也分别按各自输入 ID 的状态处理。机器人重新上传的新消息没有转发标记，始终在接收入口被过滤，防止回流。

兼容旧版按内容跳过的 `duplicate` 记录：下次启动时恢复成待处理任务，保留原输入 ID、顺序、快照和发送随机 ID；无需再转发一次。若旧任务已被之前 `--discard-pending` 的截止时间覆盖，则转换为已放弃，不恢复。`--status` 只显示旧记录及提示，不改写队列；`--no-resume` 可暂缓恢复的旧任务，`--discard-pending` 可永久放弃它们。已经确认成功或明确放弃的记录不会恢复。

若 Telegram 对不确定的旧请求只返回 `RandomIdDuplicate` 而没有返回原消息 ID，程序会保留任务并停止，不会换新随机 ID 强行重发；这种情况仍需人工核对，无法仅凭 Bot 会话保证自动确认。

当前支持普通文字、图片、视频及文件，附带的按钮和键盘会忽略，不阻塞主体备份。投票、联系人、带网页预览的消息、贴纸、阅后即焚内容、Live Photo 和自定义视频封面等会明确报错并暂停队列。文件上限与 `upload` 共用，为 2,097,152,000 字节（2000 MiB，4000 个 512 KiB 分片）；超限会在下载前显示实际大小及项目允许范围，不自动压缩或切片。此前仅因旧的 2,000,000,000 字节上限而中断、且未超过新上限的任务，重新执行 `just reupload` 即可继续。普通静态缩略图会显式下载并重新上传；Telegram 仍可能处理上传的图片，不保证最终预览逐像素一致。

## 验证

使用离线假客户端测试转发过滤、递归防护、私聊/频道隔离、批量与相册顺序、下载后上传本地字节、文字和实体保留、中断恢复与稳定 random_id、失败不越序、配置兼容和互斥。运行现有测试、格式检查、静态检查；实现阶段不登录真实 Bot 或向真实频道发送消息。
